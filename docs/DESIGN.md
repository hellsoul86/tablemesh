# TableMesh 交互与视觉设计

状态：实施设计，不代表界面已经实现。适用桌面 1280px 以上及 390px 移动视口。首版以冻结的 ENGINE-CONTRACT 为准：入座即准备，至少两席后由房主开始；独立准备、坐出、完整邀请权限和房主管理在后续 issue 实现，未实现前不显示可点击控件。

## 1. 视觉方向

主题是有社交感的深色棋牌俱乐部：深墨绿空间、暖白牌面、青绿行动状态、琥珀平台积分。界面主要内容是真实房间和牌桌，空大厅也保留直接建房入口。

建议设计令牌：背景 `#0B1514`、面板 `#142220`、桌面 `#173D36`、主文字 `#F4F1E9`、次文字 `#ABBAB5`、青绿 `#75E0BE`、琥珀 `#F2BE69`、危险 `#FF8D8D`、牌面 `#FFF9EC`。实现时验证文本对比度；颜色仅作辅助，不能让红绿颜色成为唯一状态提示。平台积分以琥珀加“积分”字样，牌桌筹码以白色圆筹码加“筹码”字样，避免把两个余额摆成同一种货币。

中文采用系统无衬线字体，金额和倒计时使用等宽数字。普通正文 14–16px，关键按钮至少 44px 高。圆角适中，牌桌可椭圆，信息面板避免到处使用大圆角卡片。节制使用发牌动效；系统减少动态效果设置生效。

## 2. 信息架构和路由

| 区域 | 路由建议 | 主要内容 | 权限 |
| --- | --- | --- | --- |
| 玩家应用 | `/app/lobby` | 可加入房间、邀请码、创建房间 | 账户，允许登录前预览可公开内容 |
| 牌桌 | `/app/rooms/:roomId` | 席位、牌局、合法动作、系统记录 | 房间访问权限 |
| 账户 | `/app/account` | 昵称、账户标识、会话、退出 | 本人 |
| 积分 | `/app/points` | 可用/冻结积分、明细、兑换网页链接 | 本人 |
| 独立商城 | `/shop` | 商品、所需积分、库存、适用说明 | 浏览可公开，兑换需登录 |
| 兑换确认 | `/redeem?sku=...` | 商品快照、积分变化、提交兑换 | 本人 |
| 兑换记录 | `/orders` | 订单状态列表 | 本人 |
| 订单详情 | `/orders/:orderId` | 处理状态、卡密展示与复制 | 订单所有者 |
| 库存运营 | `/ops/inventory` | 商品库存、CSV预览、导入结果 | 运营角色 |
| 兑换运营 | `/ops/redemptions` | 订单检索、异常状态、审计 | 运营角色 |

商城可以独立构建/部署，但路由、鉴权与共享账户关系要清晰。跨站登录只携带短期授权过程所需信息，不在 URL 放会话令牌、卡密或积分修改指令。未确定跨域部署时可先同服务不同应用入口，明确其为首版部署形态。

## 3. 桌面布局

### 3.1 大厅

顶部 64px：TableMesh 字标、当前区域、大厅/账户/积分、连接状态、账户昵称。积分只用紧凑标记呈现，不侵占建房主按钮。

内容区最大宽度约 1320px，左侧约 220px 游戏选择与筛选，中间房间列表，右侧约 280px 当前账户/最近房间/规则提示。没有足够内容时退化为两栏，不能制造虚假的热门、在线人数或占位玩家。

每个房间条目包含房名、游戏、状态、席位人数、盲注、可见性、延迟/连接提示以及“加入”按钮。公开房满员时显示“已满”；未实现观战则不显示观战入口。置顶“创建房间”和“输入邀请码”。拖拉机与麻将标“规划中”，禁用态说明尚未开放。

建房用对话框或侧板：游戏、房名、公开/邀请码、人数上限、规则预设。首版固定参数显示为只读规则摘要。确认后立即进入本人房间，不要求用户再从列表寻找。

### 3.2 牌桌

下列完整布局可展示已实现状态；v0 不提供独立准备、坐出、聊天、观战、局间补充和关闭房间按钮，除非对应服务端能力已有验收。

中心为牌桌，最多六席围绕。顶部显示房名、邀请码复制、规则版本入口、连接状态；右侧是可折叠的系统事件和手牌历史。桌面下方固定本人私牌、合法动作与数值输入。

每席展示昵称、筹码、当前投入、准备/坐出/断线状态，庄位/小盲/大盲以有文字的标记显示。当前行动者有轮廓和“行动中”标签；多行动者时全部展示“等待响应”，不以一个全局箭头表达所有规则。

桌中央显示公共牌、当前阶段、主池和可展开边池。页面明确区分“本手已投入”“剩余筹码”“底池”，避免数值方向混淆。本人手牌以暖白卡面和可读花色呈现；其他玩家手牌背面或按规则公开，后台响应本身不得包含未授权数据。

行动区固定顺序：弃牌（次要、危险说明）、过牌/跟注（主要）、下注/加注（输入后确认）。展示“跟注 20 筹码”“加注至 80 筹码”等完整语义，不能只写一个金额让人分不清是增量还是总额。滑杆辅以可输入数值与最小/半池/底池/全下快捷按钮，但每个快捷值均由合法范围约束。

不可行动时行动区展示具体原因：“等待阿青操作”“你已弃牌，本手结束后可继续”“下一手加入”。禁用按钮不代替原因文字。

### 3.3 账户和积分

账户页显示身份环境和会话状态。开发身份使用持续可见的“开发环境”标识，不模仿正式第三方登录。

积分页展示可用、冻结、最近变动，明细可按来源筛选。每项可展开订单/发放业务引用。积分为零时提供规则说明和可用的获取方式；首版没有真实获取渠道时写明“本环境积分由运营/测试发放”，不放虚假的充值按钮。

## 4. 390px 移动布局

大厅以单列房间列表呈现，游戏筛选用横向标签，建房和邀请码放在顶部固定操作行。账户和积分收进顶栏菜单；底部导航可保留大厅、积分、账户。

牌桌优先完整显示公共牌与本人动作。对手席位以紧凑两行环绕或上方网格布局，不能靠横向滚动看到关键席位。中央牌桌缩小但每张牌点数仍可读；自己的私牌靠近底部。系统事件变为可打开的底部面板，默认只展示最近一条关键事件。

行动区吸附底部安全区，最少两行：第一行额度输入/说明，第二行操作按钮。键盘展开后提交按钮仍可见。底部面板不遮盖唯一可操作入口，倒计时与当前连接状态持续可见。

订单详情单列，卡密默认掩码，点击“显示卡密”后可复制。长卡密允许换行或局部滚动，不撑破页面。复制成功用短文本反馈且不包含卡密。

## 5. 核心操作流程

### 5.1 首次开局

进入大厅 → 登录或选择开发账户 → 创建/加入房间 → 查看规则并取得席位（即准备）→ 达到人数 → 房主开始 → 本人轮到时按 legalActions 行动 → 服务端确认 → 结算摘要 → 继续下一手。

入座前告知固定初始筹码、免费规则、超时处理和断线处理。第一次进入不能用多页营销引导阻塞开局。

### 5.2 Agent 开局

Agent 获取账户 → 列房或创建房间 → 加入/取得席位 → 房主开局 → 读取本人状态与合法动作 → 按动作 schema 提交 → 收到新版本 → 等待事件或按建议间隔查询。每一步输出结构化结果和简短中文摘要。

首版动作 envelope（roomId 位于路由或工具参数，不从请求体推断账户）：

```json
{
  "requestId": "account-scoped-unique-id",
  "stateVersion": 18,
  "windowId": "betting_3",
  "action": { "type": "raise", "amount": 80 }
}
```

首版 legalActions 中的加注动作示例：

```json
{
  "type": "raise",
  "minAmount": 80,
  "maxAmount": 240,
  "allInOnly": false
}
```

`amount` 为本轮累计投入总额，绝不是追加量。行动截止时间和符合条件的席位来自 `game.window`，额度单位为筹码。首版快照为 `stateVersion`、`eventCursor`、`game` 和 `you`，`you.legalActions` 只属于当前账户。契约保留 `eligibleSeats` 集合和 `responseMode`，不会把未来游戏限制为单一行动者。

后续通用规则可扩展动作参数 schema 和可读原因；v0 不假定这些字段已经存在。Agent 不应从屏幕布局猜金额，不使用自然语言聊天文本当作执行指令。合法动作为空时，客户端根据阶段、席位和窗口显示具体等待原因。

### 5.3 兑换

进入独立商城 → 选择商品 → 阅读权益与限制 → 确认所需积分/剩余积分 → 提交一次 → 查询订单状态 → 履约成功 → 手动显示/复制卡密。

订单响应慢时保持订单引用并显示“正在确认结果”；再次打开仍是同一订单，不让用户反复点击生成新订单。卡密只在此受保护网页显示，插件界面显示“请在兑换网页查看”。

### 5.4 运营导入（完整蓝图，v0 可简化为校验后原子导入）

运营登录 → 选商品 → 选择 CSV → 本地/服务端校验预览（卡密掩码）→ 展示有效行、重复行、无效行 → 确认导入有效行或修正重传 → 显示批次 ID 与库存增量 → 可以按批次查看状态。

首版可选择全批原子拒绝或有效行部分入库，须明确一种策略并在 UI 说明；推荐全批校验通过后原子入库，便于对账。下载错误报告不得包含完整卡密。演示库存明显标“测试卡，无实际算力权益”。

## 6. 状态、错误与恢复矩阵

| 场景 | 用户看到什么 | 可做什么 | 服务器约束 |
| --- | --- | --- | --- |
| 大厅空 | 暂无房间，首个建房按钮 | 建房/输入邀请码 | 不伪造房间数据 |
| 尚未登录 | 登录后可加入牌桌 | 登录后返回原目标 | 不创建未归属席位 |
| 房间不存在/邀请码过期 | 房间不可用 | 返回大厅/重新输入 | 不泄露私密房列表 |
| 房间已满 | 6/6 已满 | 刷新/返回大厅 | 原子争抢席位，不超卖 |
| 入座人数不足 | 再来 1 位即可开局 | 分享房间标识/返回大厅 | 未满足不能开局 |
| 进行中加入 | 等待下一手 | 查看允许的公开状态/离开 | 不插入当前发牌 |
| 动作发送中 | 正在确认 | 暂时禁止重复提交 | 幂等键保证一次生效 |
| 旧版本动作 | 牌局已更新，已刷新可用动作 | 基于新视图重新选择 | 不自动把旧选择套到新局面 |
| 非法额度 | 当前可加注至 80–240 | 修正输入 | 服务端再次校验 |
| 多方响应 | 等待 2 位响应 | 在本人窗口内操作 | 不显示他人秘密提交内容 |
| 连接中断 | 连接已断开，正在恢复 | 等待/手动重连 | 动作状态未知时查询确认 |
| 恢复成功 | 已同步至最新牌局 | 继续合法动作 | 旧快照不覆盖新状态 |
| 超时 | 本轮已按规则过牌/弃牌 | 查看结果/等待下一轮 | 不自动付出筹码 |
| 筹码归零 | 本桌筹码不足 | v0 说明本席无法继续；后续提供局间补充/离席 | 不从平台积分自动扣款 |
| 积分为零 | 可用积分 0 | 查来源规则/返回免费牌局 | 不阻止免费的棋牌功能 |
| 商品缺货 | 暂时缺货 | 返回列表/查看其他商品 | 提交时再校验库存 |
| 兑换余额不足 | 还差 N 积分 | 返回积分页 | 不允许负余额 |
| 兑换网络超时 | 正在确认订单，请勿重复下单 | 查询原订单 | 原幂等键返回原订单 |
| 兑换失败 | 未完成，积分已退回/未扣除 | 查明细/重新发起 | 状态必须与账本一致 |
| 卡密已被查看 | 已在本账户展示 | 再看/复制 | 不重新进入可售库存 |
| 运营越权 | 无权限访问 | 返回账户 | API 403，前端隐藏不是鉴权 |
| 服务不可用 | 暂时无法连接，已有记录保留 | 重试/返回 | 不宣称未知订单成功或失败 |

错误结构建议包含 `code`、可读 `message`、`retryable`、`requestId`、必要时 `currentVersion`；不把堆栈、凭据、私牌、卡密写入用户错误消息。

## 7. 可访问性与可检验细节

所有按钮有明确中文可访问名称，键盘能完成建房、加入、准备、动作、兑换。对话框管理焦点，关闭后返回触发按钮；不只依赖 hover 展示规则。焦点轮廓与当前行动轮廓样式不同。

牌面使用“红桃 A”等可读文本；倒计时不用每秒对屏幕阅读器广播，只播报关键阈值。状态更新可用温和 live region；结算、错误和连接恢复以可读消息通知。按钮禁用时提供原因。涉及“全下”等操作显示明确额度，但不增加每一步都弹窗的无谓确认。

主要文字对比度达到常规可访问要求，触控目标至少约 44×44px；390px 下无整页横向滚动。减少动效设置关闭洗牌/筹码飞行动画。需要复制的信息同时提供可选中文本，复制 API 不可用时仍能手动复制。

## 8. 设计验收清单

- 实际打开桌面和 390px 页面，完成建房到结算和商品到订单详情流程。
- 使用两个独立账户，看到相同公共状态和不同私牌视图。
- 非当前行动者没有可误提交的按钮，Agent 的 legalActions 与网页按钮一致。
- 断线、超时、余额不足、缺货和重复提交均有可见结果，且与服务端记录相符。
- 插件返回数据、网络响应和日志不存在他人私牌与卡密泄露。
- 公开页面没有虚假在线人数、库存、排行榜、兼容供应商或“已上架”文案。
