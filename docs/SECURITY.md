# TableMesh security and verification boundaries

## Identity and transport

v0 has local account registration with normalized unique display names, salted password hashes and authenticated sessions. Use asynchronous node:crypto scrypt with a per-password random16-byte salt and a bounded configured work factor; use timingSafeEqual for equal-length derived keys. Validate password bounds before hashing, rate limit registration/login and never log passwords. Store only SHA-256 hashes of random32-byte session/token secrets. Sessions expire and can be revoked. Cookie sessions are distinct from game-only MCP bearer tokens; same-account scopes do not imply same privileges. No tool can request another accountId as authority. Credentials are never committed to the repository, included in screenshots, or printed in test output.

Server binds loopback by default. For v0's two Vite apps, each proxy /api to the server and cookies are on the same chosen hostname. Both apps use credentials:include. On load and refresh GET /account restores the current session; if expired, sign in and then reobserve the room. Reconnect leaves all seats and deadlines unchanged. Never re-register a replacement synthetic account on401. Cookie attributes: HttpOnly, SameSite=Strict, Path=/; Secure for HTTPS outside local development. Exact Origin allowlist protects mutations; requests lacking Origin need a valid scoped bearer rather than ambient cookies. Reject malformed cross-origin requests; no wildcard credential CORS. Authorization:Bearer wins only when explicitly supplied and validated, never fall back from an invalid bearer to a cookie. Local plain HTTP supports local testing only; live deployment needs HTTPS, credential controls and target-specific review.

MCP stdio reads TABLEMESH_TOKEN and TABLEMESH_URL. Keep these outside plugin files (environment/approved local config); only protocol messages use stdout. The adapter does not mint accounts, manage admin data, call a model API, or trust MCP transport/session IDs as authentication. Server verifies game scope at each route. Public Streamable HTTP is a future adapter requiring its proper authorization specification, Host/Origin checks and TLS; plain bearer REST behind the local stdio proxy does not claim OAuth compliance.

## Private-state isolation

The sole external room serialization function builds RoomSnapshot from publicView and authenticated own-seat privateView. It never spreads or serializes engine state. Spectators have privateState:null, legalActions:[]; other seated accounts see only their own hole cards. After a hand, folded cards remain private. Dealing and deck details have audience server or explicit seat scope and never enter public room_events. If server events support private audiences later, authorization occurs for each event and replay as well as initial subscription. Diagnostics/audit logs contain action type/version/window and actorId, never deck, raw body with secrets, private hole cards or reward codes.

An account has at most one seat per room; validate roomId ownership/membership from persisted identity. Actions are accepted only for that seat's current window. Reject user-supplied seat/account fields for action commands rather than silently forwarding them. start is owner-only; all local clients and agent clients have identical gameplay permission. One account using two clients submits competing commands, of which one wins current version; sharing a account's token intentionally shares authority and cannot be solved by labeling one client an agent.

## State, randomness and integrity

Inject shuffled decks into the pure reducer from server crypto.randomInt Fisher-Yates. Do not allow production callers to supply decks; deterministic decks are direct core test fixtures only. Validate exact52 unique cards on start. Snapshot stores remaining deck and hole cards so crashes do not reshuffle a hand. Protect database file/backup access because it contains private state. File permissions are an operational safeguard, not transport authorization. No fairness certification or server-operator-blind dealing is claimed; cryptographic commit/reveal can be a later independently designed feature.

Check requestId and canonical body hash before version. Duplicate request returns original acceptance without double action/settlement; different body with same requestId conflicts. Serialize room commands and timeout tasks. Deadline equality times out. Persist absolute deadline+windowId; scheduler cannot act on a stale window. Use safe integer chips and integer platform points, bounded below Number.MAX_SAFE_INTEGER. DB checks prevent negative balances. Core checks conservation and settlement once. Unique source keys prevent awarding the same hand twice even across crash retry. Data persistence errors rollback; return generic errors and retain action/ledger consistency.

## Rewards and operations

Practice chips never debit or credit the platform wallet. No paid buy-in, recharge, cash withdrawal or purchased-credit path is implemented. Sandbox starter points and sandbox inventory are visible as such in the UI, responses and docs. Real cards default disabled behind explicit configuration plus later economic/policy decision; flipping a flag does not establish permission or legal availability.

Store reward codes encrypted at rest using AES-256-GCM, random nonce per item, authentication tag, external key, and key-version field. Code fingerprint is keyed HMAC used for uniqueness so low-entropy card values cannot be offline-enumerated through plain hashes. Environment key absent: disable all code import/retrieval with a clear startup capability status, or permit only explicitly labeled sandbox storage in a separate local database; never silently downgrade real-code encryption. No encryption key in database/repository or frontend VITE_ variables. A test may use a generated ephemeral key without printing it. Backups need key retention and access controls; rotating keys requires tested migration/recovery.

Rewards-web code-reveal route requires the owning authenticated web session; game token is forbidden, as are another account and unauthenticated requests. Return Cache-Control:no-store on session, room-private snapshot and redemption-secret responses. Never put card codes into GET catalog/list orders/MCP outputs. Admin token is separate, externally configured and never issued by registration or login; ops UI keeps it memory-only, sends it only to exact server ops routes, and clears it on navigation/log out as appropriate. Admin logs imports/counts/targets, not inventory input. Admin endpoints disabled unless configured.

Use BEGIN IMMEDIATE and conditional inventory status update for last-stock concurrency. Reserve points+stock, assign one redemption, capture only after local delivery; rollback on failure. For an external supplier, pending holds and durable idempotency/outbox must exist before adding calls. Client cannot choose cost, account balance or code assignment. Replay provides the same redemption ID. Inventory imports have request-id dedup and product/sandbox validation. Sandbox product cannot be misrepresented as real fulfillment.

## Required negative and recovery tests

1. Anonymous and non-member observer receive no private cards/deck; own seat sees precisely2 private cards; folded cards never appear at completion; public events do not contain private details.
2. AccountA triesB's action/window, create duplicate seat, owner start as outsider, game token reads own reward code/admin routes: each denied without state changes.
3. Same accepted action twice changes version/chips once; same requestId different action conflicts; simultaneous same-version clients accept exactly one; exact deadline times out.
4. Restart server preserves account/session, stack, private cards, event cursor and deadline, and overdue automatic check/fold is applied once. Expired/revoked cookie/token denied.
5. Unique reward settlement retry generates one ledger grant. Concurrent final stock redemption has one fulfillment, one untouched losing balance. Insufficient points leaves stock available. Import/redeem retries do not duplicate codes/deductions.
6. Secret route rejects other accounts and game scopes; list/product/MCP never expose codes. Logs and frontend bundle scanning reveal no configured key/admin credential.
7. Two genuine UI browser sessions connect, join and observe separated hands. Refresh restores cookie session; stale action refreshes state and requires fresh decision. Tests use created accounts, not hardcoded account impersonation.
