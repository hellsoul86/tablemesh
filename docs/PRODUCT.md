# TableMesh 产品规划

状态：设计基线，尚不代表实现、部署或上架。首版先交付可运行、可联机、可复核的产品原型。

## 1. 定位与成立条件

TableMesh 是人和 Agent 共用的一张线上牌桌。用户通过 Codex 插件查看账户与积分、发现或创建棋牌房间、取得席位并参与游戏。独立网页承担商品浏览、预付 token 卡兑换、卡密查看和库存运营。

产品成立需要同时证明三件事：两个独立账户能完成一局真实受规则约束的牌局；同一套动作接口能供网页与 Agent 使用；牌桌筹码、平台积分及外部模型算力账单互不混账。

首款游戏是德州扑克；拖拉机、麻将通过游戏规则模块加入。不得把“当前只有一个行动者”“每步都必须轮到下一席”“所有参与者都能看全部状态”写死进房间层。

### 产品原则

- 一种账户、一种席位、一种动作协议。不给真人/Agent 建立两套余额、身份或奖励逻辑。
- 插件是联机入口和控制面，核心界面是大厅与牌桌。首页不能用宣传页代替可玩入口。
- 平台积分不是筹码；游戏筹码不是 token 卡额度；模型调用成本不自动形成平台收入或奖池。
- 规则和权益可解释。动作失败必须说明可恢复原因，积分变化必须可追溯。
- 每次开放经济能力都对应明确规则和运营条件。把功能放到外部网页不等于获得分发或经济活动许可。

## 3. 用户、账户和授权

### 3.1 统一账户

账户字段至少包括 `accountId`、昵称、状态、创建时间。身份提供方映射到内部稳定 `accountId`。用户通过网页或插件进入仍使用同一个账户。生产身份提供方未确定前，首版可使用隔离的开发账户登录，并显著显示“开发身份”，禁止据此宣称生产认证完成。

会话与账户分离，服务器从有效凭据解析身份，客户端传入的 `accountId` 不作为授权依据。退出撤销当前会话；禁用账户禁止新动作，但保留牌局和账本历史。

### 3.2 席位与动作

席位归账户所有，房主只管理房间。房主不能读取其他人的手牌、替别人下注或强制兑换。一个账户在同一房间最多一个有效席位。多个会话可以查看本人视图，但版本检查与幂等键避免同一行动重复生效。

插件操作需要显式的账户授权。代理代操可使用范围受限的授权：例如指定房间、到期时间、只读或允许游戏动作；撤销后立即禁止新动作。首版如果未实现细粒度委托，应明确只支持账户当前会话，不声称已完成委托系统。

不根据真人/Agent 标签给予优先权。检测作弊依赖可审计的行为证据，不根据模型使用与否封禁。

## 4. 三套数值体系

| 数值 | 用途 | 权威来源 | 不得发生的隐式联系 |
| --- | --- | --- | --- |
| 牌桌筹码/游戏得分 | 当前游戏的行动、胜负和计分 | 游戏规则状态与结算记录 | 筹码变化不得直接改平台积分 |
| 平台积分 | 站内权益和在获准条件下兑换商品 | 服务端双向或等价可核对账本 | 不把玩家模型开销认作充值或奖池收入 |
| token 卡面值/外部算力账单 | 外部供应商的预付权益与使用成本 | 商品说明/运营入库/供应商事实 | 不能保证卡面值等于积分、筹码或实际调用量 |

### 4.1 积分账本

余额由可审计记录构成，记录包含账户、整数变动额、来源类型、来源 ID、幂等键、时间、操作者和备注。常见类型为开发发放、运营发放、兑换冻结、冻结释放、兑换消费和退款。开发发放必须明确标识环境和用途。

建议账户呈现总额、可用、冻结三项；`可用 = 总额 - 冻结`。金额永不由浏览器直接指定，商品价格从服务端订单快照读取。相同业务幂等键只能生效一次，账本记录不覆盖不删除，纠错通过补偿记录完成。

对库存中可立即分配的卡，首版可在单个事务中完成扣分、分配卡和订单履约，减少悬挂冻结。接口和 UI 仍应区分“处理中”“已完成”“失败已退回”三类可核对状态。若使用冻结模型，则必须测试崩溃恢复和释放，不能只实现成功路径。

### 4.2 首版经济边界与待决策

首版通过免费牌局和开发积分验证玩法、账本、库存及兑换机制。演示库存必须使用无外部价值的测试卡，并在商品和详情页标明。真实兑换默认关闭，开关由运营控制，不允许客户端绕过。

尚待明确：积分的真实获取来源、兑换定价、付费入场是否存在、对局能否产生积分奖励、发行和回收责任、退款政策、地区/年龄适用范围、供应商允许的转售或分发方式、公开插件分发条件。未决部分通过独立 issue 处理；网页拆分只是一种产品职责分离。

如未来设计奖池，须明确实际出资方、收入来源、手续费、退款与对账公式。玩家给其模型服务商支付的算力费用，不经过 TableMesh 收款就不是 TableMesh 的可分配收入。

## 5. 房间全生命周期（完整蓝图）

本节描述目标生命周期；v0 只承诺建房、入座即准备、至少两席由房主开始、合法动作、结算及再开一手。独立准备、坐出、局间免费补充、房主转移、关闭/过期和完整邀请访问控制在 F02 验收。未完成能力不显示可点击按钮。

### 5.1 房间状态

`OPEN → STARTING → IN_GAME → BETWEEN_HANDS → IN_GAME`，无活跃对局后可进入 `CLOSED`。恢复过程可暴露 `RECOVERING`；不可恢复的某手标记 `ABORTED`，保留原因及日志，不伪造胜负。

房间包含游戏类型、规则版本、容量、可见性、邀请凭据、房主、成员、席位、观众策略、当前对局 ID 和房间版本。德州首版建议 2–6 席、固定盲注和初始筹码，配置由服务器校验并在开局后锁定。

### 5.2 典型流程

1. 选择游戏，创建公开房或邀请码房；展示容量、盲注、初始筹码和超时规则。
2. 账户加入房间，阅读规则并取得空席。v0 入座即准备，至少两席时由房主开始；未来独立准备模式启用后再校验各席的准备状态。
3. 服务端生成当前对局，锁定参与席位及规则版本。迟到者等待下一手，不插入进行中的发牌过程。

首版协议取舍：v0 入座即准备，由房主在至少两席时开局；以上独立准备、坐出、房主转移等完整生命周期在后续房间管理 issue 实现。前端不能为尚不存在的命令创建假操作。
4. 玩家通过其可见状态和 `legalActions` 操作。服务器验证身份、席位、版本、动作范围和阶段。
5. 规则模块结算一手，公开应公开的牌面、底池分配和摘要；保留不应公开的弃牌手牌。
6. 席位选择继续、坐出或离开。下一手参与者重新符合开局条件；筹码归零者按本房免费补充规则在两手之间申请，不能在手中补充。
7. 无活跃对局时房主可关闭。房主退出不应立即中断其他人的有效对局；可把管理权转给最早加入的可用成员，或在无人时转为等待关闭。

### 5.3 连接与时限

连接状态与游戏参与状态分离。断线不等于弃牌。重连通过事件游标或当前快照恢复，过期快照不覆盖较新状态。超时动作由游戏规则决定，德州默认可过牌则过牌，否则弃牌，绝不自动跟注、下注或加注。

每个行动窗口使用服务器截止时间，客户端倒计时仅用于展示。暂停后台页面不会延长窗口。服务重启若能恢复状态与截止时间则继续；如果不能可靠判断动作是否已生效，返回可核对状态并阻止重复执行。

聊天室或房间消息不能成为动作指令。首版可先提供系统事件和简短预设互动，完整文本聊天、举报与审核另列任务。

### 5.4 首版开局锁席位与主动离席政策

v0 德州以一手为一局。从发牌到本手结算，参赛账户与席位固定，不能让其他账户接替。点击“返回大厅”、刷新网页、网络断开不会提交离席命令，不降低信誉；保留原席位与服务端截止时间，重连恢复当前状态，超时仍按可过牌则过牌、否则弃牌处理。

只有用户在“主动放弃本局”对话框明确确认后，网页发送 `confirmAbandon:true`。非全下玩家在当前或下一合法行动窗口由服务器自动弃牌；全下玩家保留本手合法结算权益。被标记的席位显示“已放弃，结算后离席”，到本手结束前不能换人。

信誉与平台积分独立。信誉初始 100；首次主动离席信誉减少 10，且 5 分钟内不能创建房间、加入新房或开始新手；24 小时内重复主动离席信誉减少 20、冷却 15 分钟，信誉最低为 0。相同账户、房间、手牌的处罚最多记一次，冷却和处罚持久化。处罚不会扣除可兑换平台积分，也不把练习筹码转换成积分。等待阶段和两手之间离席无此处罚；冷却不阻止继续其他已经开局的牌局。

这是 TableMesh 自定义的 v0 数值，不是行业统一标准。明确退出提示与逐次加重冷却的交互参考 [PokerStars Seat Me 官方说明](https://www.pokerstars.com/help/articles/seat-me-introduction/)，不据此宣称任何平台采用上述数值。服务端对网页和 MCP 使用同一政策；账户暴露 `fairPlay`，快照暴露 `abandonedAccountIds`，客户端不能通过改标识或重试重复扣分。

## 6. 可扩展棋牌内核

房间负责身份、席位、消息传输、持久化、版本和生命周期；规则模块负责发牌、回合或窗口、合法动作、私有视图与结算。渲染器负责把规则状态展示给用户。

最低契约：

- `validateConfig(config)`：校验可配置规则与边界。
- `createGame(participants, config, randomness)`：确定初始状态与规则版本。
- `getView(state, viewer)`：返回该账户或观众允许看到的内容。
- `getLegalActions(state, actor)`：列出动作 ID、标签、参数 schema、数值范围、截止时间、窗口 ID。
- `applyAction(state, actor, action, context)`：权威验证与状态变更，生成事件和新版本。
- `resolveTimeout(state, windowId)`：按规则处理过期窗口。
- `getResult(state)`：完成、流局或中止的结构化结果。

`activeActors` 为集合，动作窗口可串行、并行提交或反应优先级；`legalActions` 不是一个全局按钮列表。窗口可要求所有玩家提交后再公开结果，以支持未来交换牌、叫牌或抢杠/吃碰杠响应。

### 首款德州的最低可玩定义

2–6 席无限注德州；庄位与盲注轮转；两张私牌；翻牌、转牌、河牌；弃牌、过牌、跟注、下注/加注、全下；下注额验证；不足额全下对重开加注权的处理；主池和边池；平局拆分与余筹码确定规则；只剩一人时无需摊牌即可结束；服务端牌型比较；一手结束后再开一手。

首版可固定盲注和初始筹码，暂不含锦标赛、重购付费、抽水、保险、双发或旁注。如果实现只覆盖简化规则，必须在游戏名及规则说明中明确“德州演示规则”，并把未覆盖的规则挂 issue，不能用“完整德州”称呼。

随机性由服务器生成，生产环境不得使用可由客户端控制的随机种子。测试可注入确定性牌序以复现边池和平局等情景。公开审计不得泄露未公开的牌序。

### 拖拉机、麻将的规划约束

拖拉机需要搭档关系、主牌、抢庄/叫主、甩牌合法性、得分牌和跨局升级。麻将需要多人反应窗口、优先级、秘密信息、不同地方规则与多家和牌配置。两者先各自写规则版本和测试样例，再接入现有房间，不能靠追加德州专用字段完成。

## 7. 独立商城、兑换与运营

商城与兑换是独立导航区域，部署时可独立站点或域名；共用账户服务和服务端积分账本。插件只提供安全链接和必要的账户状态，不返回卡号、卡密、完整库存或可推导卡密的日志。

### 7.1 商品和库存

商品包含供应商名称、面值/权益说明、所需积分、适用条件、有效期规则、退款说明、上架状态和可售数量。未确定供应商时只提供明确的演示商品，不编造兼容性。

运营方导入预付卡库存，首版可支持受限 CSV：商品 SKU、卡片参考号、卡密、有效期、批次备注。服务器校验缺失字段、无效日期、同批重复和跨批重复；返回成功/拒绝计数及不含密钥的错误行。完整运营版本在导入前展示预览并显式确认入库；v0 可先完成严格校验后的原子导入与脱敏结果，完整 CSV 预览另列 F04。使用卡密指纹识别重复，指纹不作为对外可用凭据。

卡密应在服务端加密存储，密钥来自部署配置而非源码。运营列表仅显示批次、库存状态和掩码；不需要日常明文浏览权限。测试库存与真实库存隔离。导入和读取卡密均留审计，但日志不含卡密。

### 7.2 兑换流程

1. 商品页展示当前价格、余额、库存、权益与使用条件；用户发起兑换。
2. 确认页再次展示消耗积分、兑换后余额和商品快照；不足余额或缺货时不能提交。
3. 服务端以幂等键创建订单，原子检查余额与库存，扣分或冻结，并唯一分配一张卡。
4. 成功后跳至订单详情。只有订单所属账户通过兑换网页的受保护接口可解密查看卡密；插件工具层不暴露此接口。
5. 网络超时时按同一订单/幂等键查询结果，不能直接生成第二单。用户手动重试仍返回原结果。
6. 不可履约则回滚或释放积分，状态和账本能证明未多扣。已展示的卡不得自动放回可售库存。

建议订单状态：`PROCESSING`、`FULFILLED`、`FAILED_REFUNDED`、`CANCELLED`；若引入人工处理，使用 `NEEDS_REVIEW`，页面解释原因和处理入口。状态机必须约束合法迁移，不能允许“已履约”直接变回“待售”。

### 7.3 运营与反串通

运营入口使用独立角色校验；普通账户访问必须由服务器拒绝。至少具备商品上下架、库存导入/失效、兑换检索、账本查询、人工补偿和审计查看。首版无真实资产时可先关闭人工补偿入口，但不能给普通用户一个可修改任意余额的通用接口。

牌局记录保留动作、参与账户、席位、时间、规则版本和结果；观众与公开回放遵循私密牌信息边界。相同设备或网络只能作为辅助信号，不能单独认定作弊。串通识别规划关注固定搭档异常转移筹码、异常弃牌、重复关联房间和奖励套利，并支持人工复核、申诉、最小必要留存。先验证玩法，不开放容易被刷的按胜负发积分规则。

## 8. 成功指标与验收证据

| 指标 | 定义 | 首版验证方式 |
| --- | --- | --- |
| 联机闭环成功 | 两个独立账户从加入到结算至少一手 | 两个隔离浏览器会话与服务器事件记录 |
| Agent 可操作性 | 仅凭本人视图和 legalActions 能完成合法动作 | 工具或 API 调用演示，记录动作 ID/版本 |
| 隐私正确性 | 他人视图及插件结果无私牌/卡密泄露 | 针对接口响应的断言，不能只看前端隐藏 |
| 动作一致性 | 重复请求只生效一次，旧版本被拒绝 | 重试、并发和陈旧版本测试 |
| 结算可信性 | 总筹码守恒，主边池和并列分配正确 | 确定性场景与整数守恒断言 |
| 兑换一致性 | 一次扣分对应唯一订单和卡 | 重复提交、库存竞争、余额不足测试 |
| 恢复能力 | 重连回到当前状态且能继续 | 断网/刷新和服务端状态对照 |
| 易用性 | 桌面和 390px 宽度能完成主要动作 | 实际截图与操作，不只构建成功 |

运营后再采集建房到开局转化、开局等待时长、完成率、每局超时率、断线恢复率、兑换失败率和客服处理时长。首版不虚构 MAU、留存或收入目标值。

## 9. 版本分期

- **v0 可用原型**：统一开发账户、入座即准备、可玩大厅/牌桌、真实多账户联机、德州规则、legalActions、基础插件接口、独立积分账本、演示库存导入和兑换闭环、桌面与移动验证。交付可运行代码和证据，真实兑换默认关闭。
- **v0.1 运营准备**：正式身份接入、生产密钥与部署配置、审计/备份恢复、细粒度授权、监控、经济规则和分发核验，真实商品与适用条件明确后才申请对应启用动作。
- **v0.2 多棋牌**：规则契约回归测试、拖拉机和麻将各自规则实现；多方响应和搭档结构经实局验证。
- **v1 分发与规模**：获准分发渠道、稳定运行指标、作弊处置、客服与申诉，以及另行明确的经济能力。

每期的发布、上架和生产启用是独立交付动作。代码存在、测试通过、仓库公开、演示在线、目录上架和真实资产可用分别陈述。
